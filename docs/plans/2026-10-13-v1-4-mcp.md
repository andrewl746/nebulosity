# V1.4 MCP Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve Nebulosity's engine to Claude Code and any MCP client: one tool registry (`overview`, `describe`, `search`, `dependents`, `dependencies`, `path`, `show_on_map`), an MCP server over stdio that reads the database read-only while the Map's background worker writes, the `claude mcp add` line for Windows, macOS and Linux, S5 (≤ 500 ms warm) measured on VS Code, and every tool exercised once through `claude -p`. Every tool answers without summaries (free mode, ADR-043).

**Architecture:** Three new layers, each thin over the one below.
- **Engine** (`lib/engine/`): `reach.ts` adds dependents, dependencies and import chains by breadth-first search over a compressed copy of the import graph that describe already loads once per index version; `overview.ts` adds the repo's first answer.
- **Tools** (`lib/tools/`): `registry.ts` defines each tool once (name, an LLM-facing description, a zod schema, a handler). Handlers return text, the paths they touched and, for `show_on_map`, a UI action. They never touch the network. `answers.ts` turns engine results into compact text; `repo.ts` picks the repo for each call.
- **Adapter** (`mcp/`): `server.ts` registers the registry's entries with the official MCP SDK, posts one live event per call to the Map, and maps errors to MCP error results. `launch.mjs` is the command Claude Code runs: `node <checkout>/mcp/launch.mjs`.

**Tech Stack:** TypeScript 5, Node 24 (tested), `@modelcontextprotocol/sdk` **1.32.1** (new, pinned exactly; released 2026-10-05, accepts zod 3.25 or 4), zod 4.5, better-sqlite3 + Drizzle (WAL), tsx 4.23, Vitest 4. The LangGraph wrapper over the same registry is E1's.

**Spec:** `docs/PIVOT_SPEC.md`: §2 (S5), §3 (rules 2, 4, 5), §6 (queries and the registry), §8 (the live channel), §11 (the smoke test), §12–§13. Decisions ADR-030 (one registry, two adapters), ADR-039 (the live channel, amended 2026-10-13), ADR-043 (free mode), ADR-008 (UI actions); `docs/API_CONTRACTS.md` §14. This plan adds ADR-044 → ADR-048 and `API_CONTRACTS.md` §17, and amends ADR-030. The fixture's ground truth is the V1.1 plan's (`docs/plans/2026-10-11-v1-1-engine-foundation.md`, "Fixture ground truth"); the answers derived from it for this slice are below.

## Decisions for the owner (settle these before Task 1)

The plan is written for the recommended option in each. A different pick changes the tasks named.

### D1. Which repo a call answers about, and which port the live events go to

**Recommended:** each call works it out afresh.
- **The repo** is the indexed repo holding Claude Code's project folder. Claude Code sets `CLAUDE_PROJECT_DIR` for the MCP servers it starts; other clients get the server's working folder. When indexed repos nest, the deepest wins. Folders compare by forward-slash spelling, without a trailing slash, and case-insensitively on Windows.
- **Otherwise** the call answers about the Map's active repo (`activeRepo` in `.nebulosity/config.json`), and the answer's first line says so, naming both folders. Otherwise it's an error: nothing indexed yet.
- **Read per call.** The repo list (the database) and the config are read on every call, so `npm run index` or the Map's repo menu take effect without restarting Claude Code.
- **The port** is `config.port` (default 3000), read per call. Live events go out only when the answering repo is the one the Map shows; otherwise `show_on_map` says the Map shows another repo. Live events carry paths but no repo (§14), so an event about one repo would light up boxes with the same paths in another.

**Alternatives:**
- (a) Always the Map's repo. Simplest, but Claude Code opened in repo B would answer about repo A, and nothing would say so.
- (b) A `repo` argument on every tool: more for the model to get wrong, on every call.
- (c) A repo fixed in the registration (`-e NEBULOSITY_REPO=…`): one registration per repo.

**If you pick (a):** Task 5 shrinks to reading the config, ADR-046 changes, and the "other repo" note goes.

### D2. Opening the database read-only while the background worker writes

**Recommended:**
- **The open.** `openDb(file, "readonly")`: better-sqlite3 with `readonly: true, fileMustExist: true`, no pragmas, no migrations. The file is already in WAL mode (the writers set it, and it persists in the file), so the MCP server reads while the worker writes, and every query sees the newest commit.
- **A current schema.** Before use, it checks that drizzle's `__drizzle_migrations` table holds this checkout's newest migration. If not, every tool answers "start the Map (npm run dev) or run npm run index once" (both migrate), instead of failing later on a missing column.
- **No index yet.** A missing file means nothing is indexed yet. A failed open isn't kept, so once the user indexes, the same server works without a restart.
- **Caches.** Every in-memory cache is keyed on the index version (ADR-036) or the vector stamp, so the worker's writes reach the next answer. The new reach index follows the same rule.

**Tested:** on temp files (writes refused, another connection's later commits seen, an outdated file, a never-migrated file, a missing file), and end to end over stdio (every tool through a read-only server).

**Alternatives:**
- (a) Open read-write and set `query_only`: the open itself would still set WAL and migrate.
- (b) Let the MCP server migrate too: a Claude Code session could change the schema under a running Map. Two schema owners is exactly ADR-023's revisit trigger.
- (c) Copy the database per session: stale at once.

### D3. The launch command and the `claude mcp add` line

**Recommended:** a plain-JavaScript launcher, `mcp/launch.mjs`, run by `node`.
- **What it does.** It sets `NEBULOSITY_HOME` to the checkout it sits in, unless that's already set. Then it imports tsx from the checkout's `node_modules` (an ESM import resolves next to the importing file, not from the working folder) and runs `mcp/server.ts`.
- **No `npx`, so no `cmd /c`.** The `cmd /c` wrapper exists for `npx`, a `.cmd` batch file on Windows; `node.exe` runs directly. The same line works on macOS and Linux.
- **Probed today.** A throwaway script started from a folder outside the checkout loaded tsx in 51 ms and `lib/engine/describe.ts` with its whole import tree in 0.44 s.

**For you now:** local scope, run from `../vscode`, so the server only loads in VS Code sessions (not in every session in this checkout):

```
claude mcp add --scope local --transport stdio nebulosity -- node <checkout>/mcp/launch.mjs
```

**For the README:** the same line with `--scope user` and the reader's path, which serves every indexed repo through D1.
- Forward slashes work in every Windows shell (Git Bash drops backslashes); quote a path with spaces.
- `-e NEBULOSITY_LIVE=off` keeps tool calls off the Map. It goes before `--transport`: the CLI reads a name that follows `--env` directly as another pair.
- `claude mcp add` writes to your `~/.claude.json`, so Task 10 asks you first (or you run it yourself).

**Alternatives:**
- (a) `cmd /c npx tsx C:/…/mcp/server.ts`: a Windows-only line, and npx's lookup on every start. tsx would be found only if the working folder has it.
- (b) A compiled `dist/` run by plain `node`: no tsx at run time, but a build step. V1.6's package decides that.

### D4. The answer format (§6.2: compact text, exact totals, truncation markers, a freshness note last)

**Recommended rules** (they become `API_CONTRACTS.md` §17; "Ground truth" below shows every tool's answer on the fixture):
- **Text.** Plain text, no Markdown. Paths are repo-relative, and folders end in `/`.
- **Counts.** Exact, with thousands separators. Totals are always complete, even when a list is cut.
- **Cut lists.** Lists end with `… 4,231 more`, plus `(next page: offset 50)` where the tool pages.
- **Size.** Every answer stays under 40,000 characters. Claude Code moves a result of 50,000 or more into a file the model has to read back, and warns past 10,000 tokens.
- **Notes.** Notes are `Note: …` lines. The tool's own notes come after the answer, then the index note (an update running or failed), then the stale-summary note, last. The one exception: when the project folder didn't pick the repo, that note comes first, because everything after it is about another repo.
- **Free mode.** Where a summary would go: `Summary: none — summaries are off (no ANTHROPIC_API_KEY); a key adds a short summary of every file and folder.` Search says it used code and folder names only.
- **Errors.** Errors are MCP error results (`isError: true`), one sentence each.

**Alternatives:**
- (a) JSON (`structuredContent`): exact, but 2–3 times the tokens, and harder for a model to skim.
- (b) Markdown tables: tokens spent on pipes and dashes.

### D5. How S5 is measured

**Recommended:** `npm run bench-mcp -- ../vscode`.
- **The run.** The MCP SDK's stdio client starts the real server in VS Code's folder, with live events off, and times each call from the request sent to the answer parsed.
- **Cold and warm.** Each tool's first call in the session is reported apart: it may load the import graph or the embedding model. The next 20 calls per tool, on fixed VS Code inputs (Task 9), are warm.
- **The pass.** S5 passes when every warm call is ≤ 500 ms: the max, not the p95.
- **The table** also gives p50 and p95, each tool's first call, the server's start-up time and the largest answer in characters.

**Why "after each tool's first call"** rather than the spec's "after the first call of a session": the first `search` loads the MiniLM model (about 1–2 s), so on the literal reading S5 would depend on the order of the calls.

**Alternatives:**
- (b) Keep the literal reading and preload the model when the server starts: about 100 MB and a second of CPU in every Claude Code session, whether search is used or not.
- (c) Judge the p95 instead of the max.

### D6. The `claude -p` smoke test, and how many calls it spends

**Recommended:**
- **Free checks first.** After registering, `claude mcp get nebulosity` and `claude mcp list`. They start the server and check the handshake; no model calls.
- **Then 1 `claude -p` run** from `../vscode`, on Sonnet (`--model sonnet`):
  - only this server (`--strict-mcp-config --mcp-config <ledger>/mcp-smoke.json`), with live events off;
  - no built-in tools (`--tools ""`), and `ENABLE_TOOL_SEARCH=false` so the seven tools load up front;
  - `--allowedTools mcp__nebulosity` and `--max-turns 12`.

  The prompt asks for each tool exactly once, in order, then a one-line verdict per tool. That's about 8–9 model turns inside the one call. Claude Code's estimate (`total_cost_usd`) and the token counts are recorded.
- **At most 1 retry**, if a fix is needed.
- **Optionally 1 more**, with live events on, while you watch the Map. Only if you want to see it.

**So:** 1 run expected, at most 2 without the demo, 3 with it.

### Rulings already made (say if you disagree)

- **R1. Free mode comes from the index, not from the server's environment.**
  - `summariesOff` means the stored summaries stage is `off`, which `npm run index` and the worker write when there's no key.
  - The MCP server never loads `.env.local`, so it never holds the API key.
- **R2. Your Phase 5 tools stay as they are.** `lib/agent/tools.ts` is left untouched until E1, which wraps the registry; `lib/agent/state.ts` isn't touched at all.
- **R3. The dependency tools take folders, order by importance and page.**
  - `dependents`, `dependencies` and `path` take folders as well as files.
  - Lists go nearest first, then most imported, then by path.
  - `limit` (1–500, default 50) and `offset` page long lists.
  - `path` tries the other direction when the first finds nothing.
- **R4. Search's notes are corrected for free mode.** They now say "code and folder names only", and "summaries are off" when there's no key. The change is in the engine, so the Map's search palette says the same.
- **R5. The SDK is pinned exactly.** `@modelcontextprotocol/sdk` 1.32.1: the newest (2026-10-05), and it accepts zod 4.

## Review Focus

Five inputs or conditions most likely to hurt a real user that the spec doesn't spell out. Each line names the test that pins it.

1. **Anything but protocol on stdout.** A library's `console.log`, or a stray debug print, breaks the JSON-RPC stream, and Claude Code drops the server.
   - Task 7: `keepStdoutForProtocol` sends `console.log`, `info` and `debug` to stderr (tested).
   - Task 8: the stdio test fails on any transport error, including a line on stdout that isn't JSON.
   - Task 9: the bench runs search with real vectors through the server, so MiniLM and onnxruntime run there. Any output of theirs on stdout fails the bench.
2. **Claude Code's project folder spelled differently from the stored root.**
   - Windows case and backslashes: `c:\users\dev\code\vscode\src` against `C:/Users/dev/code/vscode`.
   - A trailing slash.
   - A sibling sharing a prefix (`vscode-docs` isn't inside `vscode`).

   Pinned by Task 5's `chooseRepo` tests.
3. **An index older than the checkout.** After a `git pull` with a new migration, while Claude Code is open, the answer must say what to run, not "no such column". Pinned by Task 1's outdated and never-migrated tests.
4. **Claude Code connected before anything is indexed.** The server must start, list its tools and answer "No repository indexed yet…", then work once the user indexes, without a restart. Pinned by Task 8's stdio test.
5. **Huge answers.** A hub with thousands of importers, a folder with 780 children, a file with hundreds of declarations, long paths: each answer stays under 40,000 characters, and the cut line gives the right next offset.
   - Task 4's budget test: 600 entries of 100-character paths.
   - The caps in `describeAnswer` (Task 4).
   - Task 9 records the largest answer per tool on VS Code.

import fs from "fs";
import path from "path";
import Database from "better-sqlite3";
import { drizzle } from "drizzle-orm/better-sqlite3";
import { migrate } from "drizzle-orm/better-sqlite3/migrator";
import { readMigrationFiles } from "drizzle-orm/migrator";
import * as schema from "./schema";
import { nebulosityPath } from "../home";

/** How a process opens the database. Everything writes except the MCP server, which only reads (ADR-030, ADR-044). */
export type DbMode = "readwrite" | "readonly";

/** A read-only open found no database file: nothing has been indexed on this machine yet. */
export class DatabaseMissingError extends Error {
    constructor(file: string){
        super(`No repository indexed yet: there's no index at ${file}. In the Nebulosity folder, run npm run index -- <path-to-repo>.`);
        this.name = "DatabaseMissingError";
    }
}

/**
 * A read-only open found a database behind this checkout's migrations. A reader may not migrate (only the Next server
 * and the CLI own the schema, PIVOT_SPEC.md §3), and reading on would fail later on a missing column.
 */
export class DatabaseOutdatedError extends Error {
    constructor(){
        super("Nebulosity's index is older than this version of Nebulosity. Start the Map (npm run dev) or run npm run index once in the Nebulosity folder to update it, then try again.");
        this.name = "DatabaseOutdatedError";
    }
}

const migrationsFolder = (): string => nebulosityPath("lib", "db", "migrations");

const connect = (sqlite: Database.Database) => drizzle(sqlite, { schema });

/** The database handle every store function takes. */
export type Db = ReturnType<typeof connect>;

/**
 * Opens a database file, or ":memory:" for a throwaway one.
 * - readwrite: WAL, NORMAL sync, foreign keys, then any pending migration (ADR-023).
 * - readonly (the MCP server, ADR-044): the file must exist and be fully migrated, and nothing is written, not even a
 *   pragma. The file is already in WAL mode (a writer set it, and the mode persists in the file), so it reads while the
 *   background worker writes, and every query sees the newest commit.
 */
export function openDb(file: string, mode: DbMode = "readwrite"): Db {
    if (mode === "readonly") return openReadOnly(file);

    if (file !== ":memory:") fs.mkdirSync(path.dirname(file), { recursive: true });
    const sqlite = new Database(file);
    sqlite.pragma("journal_mode = WAL");
    // NORMAL is SQLite's recommended pairing for WAL: still corruption-safe, but a
    // commit no longer waits for an fsync. Indexing VS Code commits ~30 batches, and
    // FULL would make every one of them wait on the disk.
    sqlite.pragma("synchronous = NORMAL");
    sqlite.pragma("foreign_keys = ON");

    const db = connect(sqlite);

    // Migrate every database, not just the in-memory test one. Drizzle records
    // applied migrations in its own table, so this is idempotent and cheap on an
    // already-current file, and it is what makes "delete the .db file and it
    // self-heals on the next request" (Phase D's acceptance criterion) actually
    // true. Migrating only :memory: also meant schema drift could never be
    // caught by the test suite, because the tests were the only thing running
    // the migrations at all.
    migrate(db, { migrationsFolder: migrationsFolder() });

    return db;
}

function openReadOnly(file: string): Db {
    if (!fs.existsSync(file)) throw new DatabaseMissingError(file);
    const sqlite = new Database(file, { readonly: true, fileMustExist: true });
    try{
        assertMigrated(sqlite);
    } catch (err){
        sqlite.close();
        throw err;
    }
    return connect(sqlite);
}

/**
 * Every migration this checkout has must already be applied. Drizzle records each one in __drizzle_migrations with its
 * folder's timestamp and applies those newer than the newest recorded; this asks the same question and applies nothing.
 */
function assertMigrated(sqlite: Database.Database): void {
    const newest = Math.max(...readMigrationFiles({ migrationsFolder: migrationsFolder() }).map((m) => m.folderMillis));
    let applied: number | null = null;
    try{
        const row = sqlite.prepare("select max(created_at) as at from __drizzle_migrations").get() as { at: number | string | null };
        applied = row.at === null ? null : Number(row.at);
    } catch{
        // no such table: this file was never migrated
    }
    if (applied === null || applied < newest) throw new DatabaseOutdatedError();
}

const globalForDb = globalThis as unknown as { db?: Db; readOnly?: boolean };

/** The MCP server's first act (ADR-044): this process only reads. It must come before the database is first opened. */
export function useReadOnlyDatabase(): void {
    if (globalForDb.db && !globalForDb.readOnly) throw new Error("useReadOnlyDatabase() must run before the database is first opened.");
    globalForDb.readOnly = true;
}

export function getDb(): Db {
    if (!globalForDb.db){
        // Vitest gets a throwaway in-memory database, whatever the mode: a test never opens a real file through here.
        // Everything else opens the file under NEBULOSITY_HOME (lib/home.ts), never relative to cwd, because the MCP server
        // is launched from inside the user's repository. A failed open isn't kept, so the next call tries again: the MCP
        // server may start before anything is indexed.
        globalForDb.db = process.env.VITEST
            ? openDb(":memory:")
            : openDb(nebulosityPath(".nebulosity", "nebulosity.db"), globalForDb.readOnly ? "readonly" : "readwrite");
    }

    return globalForDb.db;
}

```markdown
## ADR-044 — The MCP server opens the database read-only (‹today›) — amends ADR-023 and ADR-030

**Context:** ADR-030 and PIVOT_SPEC.md §3 (rule 5) said the MCP server reads the database and never migrates, without saying how. Claude Code starts the server once per session, and it may outlive many writes by the Map's background worker (ADR-038) or the CLI. ADR-023 migrates on every open, which a reader must not do: two processes owning one schema is the revisit trigger ADR-023 named.
**Decision:**
- `openDb(file, "readonly")` opens with better-sqlite3's `readonly` and `fileMustExist`, sets no pragmas and runs no migrations. The file is already in WAL mode (a writer set it, and the mode persists), so it reads while the worker writes, and each query sees the newest commit.
- It checks the file is current: this checkout's newest migration must be in drizzle's `__drizzle_migrations`. If not, `DatabaseOutdatedError` tells the user to start the Map or run `npm run index` once, since both migrate.
- No file is `DatabaseMissingError`: nothing indexed yet. A failed open isn't kept, so the server recovers without a restart once something is indexed.
- The MCP entry point calls `useReadOnlyDatabase()` before anything opens the database. Tests keep their in-memory database.
**Alternatives:** (a) A normal open plus `pragma query_only`: the open would still set WAL and migrate. (b) Let the MCP server migrate as well: a Claude Code session could change the schema under a running Map. (c) A copy of the database per session: stale at once.
**Consequences:** A long-lived reader's caches stay correct only because they're keyed on the index version (ADR-036) or the vector stamp; new caches must follow that rule (ADR-045's import index does). After a pull that brings a migration, the tools answer with the update sentence until the Map or the CLI runs once.
**Revisit when:** the data moves out of the checkout (V1.6's package or the desktop app), so the migrations folder and the database no longer share `NEBULOSITY_HOME`.
```

import path from "path";
import { getDb, type Db } from "../db/client";
import { loadFileInfo, loadFolderInfo } from "../db/store/map";
import { loadImportEdgesFrom, requireRepository } from "../db/store/structure";
import { readIndexVersion } from "../db/store/version";
import { repoKey } from "../index/paths";
import { BadInputError } from "./errors";
import { importGraphFor, rangeOf, type ImportGraph, type TargetKind } from "./graph";
import { PathNotFoundError } from "./level";

/** Which way an answer follows imports: to the files that import the target, or to the files it imports. */
export type Direction = "dependents" | "dependencies";

/** One direction of the graph as compressed rows: node i's neighbours are neighbours[offsets[i] .. offsets[i + 1]), in path order. */
export type Adjacency = { offsets: Int32Array; neighbours: Int32Array };

/** The import graph ready for walking (PIVOT_SPEC.md §6.1): both directions, and how many files import each file. */
export type ImportIndex = { paths: string[]; imports: Adjacency; importedBy: Adjacency; inDegree: Int32Array };

/** A file reached from a target, and how many imports away it is. */
export type Reached = { path: string; distance: number };

/** dependents or dependencies of one file or folder (ADR-045): every file reached, ordered, and how many directly. */
export type ReachAnswer = { path: string; kind: "folder" | "file"; direction: Direction; reached: Reached[]; direct: number; indexVersion: number };

/** How one place reaches another through imports (ADR-045). */
export type ChainAnswer = {
    from: string;
    fromKind: "folder" | "file";
    to: string;
    toKind: "folder" | "file";
    /** forward: `from` reaches `to`; reverse: only `to` reaches `from`; none: neither does. */
    found: "forward" | "reverse" | "none";
    /** The chain in import order, importer first; empty when none. */
    files: string[];
    /** specifiers[i] is how files[i] imports files[i + 1], as written in its source. */
    specifiers: string[];
};

/** Rows of `to` per `from`, counting first, then filling, then sorting each row so walks are deterministic. */
function adjacency(count: number, from: Int32Array, to: Int32Array): Adjacency {
    const offsets = new Int32Array(count + 1);
    for (let i = 0; i < from.length; i++) offsets[from[i] + 1]++;
    for (let i = 0; i < count; i++) offsets[i + 1] += offsets[i];
    const next = offsets.slice(0, count);
    const neighbours = new Int32Array(from.length);
    for (let i = 0; i < from.length; i++) neighbours[next[from[i]]++] = to[i];
    for (let i = 0; i < count; i++) neighbours.subarray(offsets[i], offsets[i + 1]).sort();
    return { offsets, neighbours };
}

export function buildImportIndex(graph: ImportGraph): ImportIndex {
    const count = graph.paths.length;
    const inDegree = new Int32Array(count);
    for (const target of graph.targets) inDegree[target]++;
    return {
        paths: graph.paths,
        imports: adjacency(count, graph.sources, graph.targets),
        importedBy: adjacency(count, graph.targets, graph.sources),
        inDegree,
    };
}

/** Kept per graph object: a new index version loads a new graph, so it gets a new index (ADR-044's rule for caches). */
const indexes = new WeakMap<ImportGraph, ImportIndex>();

export function importIndexFor(db: Db, repoId: number, version: number): ImportIndex {
    const graph = importGraphFor(db, repoId, version);
    let index = indexes.get(graph);
    if (!index){
        index = buildImportIndex(graph);
        indexes.set(graph, index);
    }
    return index;
}

/**
 * Every file reached from a target by following imports one way, breadth-first (PIVOT_SPEC.md §6.1): nearest first,
 * then the most imported (ADR-010's importance), then by path. The target's own files are the start, never the answer.
 */
export function reachFrom(index: ImportIndex, targetPath: string, kind: TargetKind, direction: Direction): Reached[] {
    const [from, to] = rangeOf(index, targetPath, kind);
    const edges = direction === "dependents" ? index.importedBy : index.imports;
    const distance = new Int32Array(index.paths.length).fill(-1);
    const reached: number[] = [];

    let frontier: number[] = [];
    for (let i = from; i < to; i++){
        distance[i] = 0;
        frontier.push(i);
    }
    for (let d = 1; frontier.length > 0; d++){
        const next: number[] = [];
        for (const node of frontier){
            for (let e = edges.offsets[node]; e < edges.offsets[node + 1]; e++){
                const other = edges.neighbours[e];
                if (distance[other] !== -1) continue;
                distance[other] = d;
                next.push(other);
                reached.push(other);
            }
        }
        frontier = next;
    }

    // positions are in path order, so a - b is "by path"
    return reached
        .sort((a, b) => distance[a] - distance[b] || index.inDegree[b] - index.inDegree[a] || a - b)
        .map((i) => ({ path: index.paths[i], distance: distance[i] }));
}

/**
 * The shortest chain of imports from any file in `from` to any file in `to`, or null (PIVOT_SPEC.md §6.1). Breadth-first
 * from every start at once, neighbours in path order, so equally short chains always resolve to the same one.
 */
export function shortestChain(index: ImportIndex, from: [number, number], to: [number, number]): string[] | null {
    const parent = new Int32Array(index.paths.length).fill(-2);   // -2 unseen, -1 a start
    const queue: number[] = [];
    for (let i = from[0]; i < from[1]; i++){
        parent[i] = -1;
        queue.push(i);
    }
    for (let head = 0; head < queue.length; head++){
        const node = queue[head];
        for (let e = index.imports.offsets[node]; e < index.imports.offsets[node + 1]; e++){
            const next = index.imports.neighbours[e];
            if (parent[next] !== -2) continue;
            parent[next] = node;
            if (next >= to[0] && next < to[1]){
                const chain = [next];
                for (let at = node; at !== -1; at = parent[at]) chain.push(at);
                return chain.reverse().map((i) => index.paths[i]);
            }
            queue.push(next);
        }
    }
    return null;
}

/** What a path is in the index, or null when nothing is indexed there. */
function kindAt(db: Db, repoId: number, targetPath: string): TargetKind | null {
    if (loadFolderInfo(db, repoId, targetPath)) return targetPath === "" ? "repo" : "folder";
    return loadFileInfo(db, repoId, targetPath) ? "file" : null;
}

function requireKind(db: Db, repoId: number, targetPath: string): TargetKind {
    const kind = kindAt(db, repoId, targetPath);
    if (kind === null) throw new PathNotFoundError(targetPath);
    return kind;
}

/** What each path is (repo, folder or file), or null where nothing is indexed: show_on_map's check. */
export function targetKinds(repoRoot: string, paths: readonly string[]): (TargetKind | null)[] {
    const db = getDb();
    const repoId = requireRepository(db, repoKey(path.resolve(repoRoot)));
    return paths.map((p) => kindAt(db, repoId, p));
}

/** dependents and dependencies (PIVOT_SPEC.md §6.1, ADR-045). The whole repo has no outside, so it's refused. */
export function reach(repoRoot: string, targetPath: string, direction: Direction): ReachAnswer {
    const db = getDb();
    const repoId = requireRepository(db, repoKey(path.resolve(repoRoot)));
    // one read transaction: the version and the graph it names are one consistent picture
    return db.transaction(() => {
        const kind = requireKind(db, repoId, targetPath);
        if (kind === "repo") throw new BadInputError("Pass a folder or a file: the whole repo has nothing outside it.");
        const version = readIndexVersion(db, repoId);
        const reached = reachFrom(importIndexFor(db, repoId, version), targetPath, kind, direction);
        return { path: targetPath, kind, direction, reached, direct: reached.filter((r) => r.distance === 1).length, indexVersion: version };
    });
}

/** path (PIVOT_SPEC.md §6.1, ADR-045): the shortest chain from `from` to `to`, or else from `to` to `from`, or none. */
export function importChain(repoRoot: string, fromPath: string, toPath: string): ChainAnswer {
    const db = getDb();
    const repoId = requireRepository(db, repoKey(path.resolve(repoRoot)));
    return db.transaction(() => {
        const fromKind = requireKind(db, repoId, fromPath);
        const toKind = requireKind(db, repoId, toPath);
        if (fromKind === "repo" || toKind === "repo") throw new BadInputError("Pass two folders or files: the whole repo holds everything.");
        const index = importIndexFor(db, repoId, readIndexVersion(db, repoId));
        const a = rangeOf(index, fromPath, fromKind);
        const b = rangeOf(index, toPath, toKind);
        if (a[0] < b[1] && b[0] < a[1]) throw new BadInputError(`"${fromPath}" and "${toPath}" overlap: one holds the other. Pick two places side by side.`);

        const forward = shortestChain(index, a, b);
        const reverse = forward ? null : shortestChain(index, b, a);
        const files = forward ?? reverse ?? [];
        return {
            from: fromPath, fromKind, to: toPath, toKind,
            found: forward ? "forward" : reverse ? "reverse" : "none",
            files,
            specifiers: specifiersAlong(db, repoId, files),
        };
    });
}

/** How each file of a chain imports the next, as written in its source. */
function specifiersAlong(db: Db, repoId: number, files: readonly string[]): string[] {
    const specifiers: string[] = [];
    for (let i = 0; i + 1 < files.length; i++){
        const edge = loadImportEdgesFrom(db, repoId, [files[i]]).find((e) => e.target === files[i + 1]);
        specifiers.push(edge?.specifier ?? "");
    }
    return specifiers;
}

```markdown
## ADR-045 — Import reach: folders as well as files, exact totals, nearest and most-imported first, paged (‹today›) — amends PIVOT_SPEC.md §6.1

**Context:** §6.1 asks for `dependents`/`dependencies` (a breadth-first search over an in-memory adjacency list, cached per index version, with an exact total and then the top entries by distance) and `path` (the shortest chain, in either direction, or "no path"). Building them raised four questions: can a target be a folder, how entries at one distance are ordered, how an agent gets more than one answer's worth, and which chain comes back when several are equally short.
**Decision:**
- **Targets.** A file or a folder. A folder's files are the start, and none of them is ever listed, so "what imports `src/vs/base`" means files outside it. The whole repo has no outside and is refused.
- **Totals.** Every answer counts all the files reached and the direct ones, however many are listed.
- **Order.** Nearest first, then the most imported (in-degree, ADR-010), then by path, so a cut list shows the most central files.
- **Paging.** `limit` (1–500, default 50) and `offset`. The cut line names the next offset.
- **Chains.** Breadth-first from every file of `from` at once, neighbours in path order, so the same chain comes back every time. When `from` doesn't reach `to`, the other direction is tried, and the answer says which way the chain runs. Places that overlap are refused.
- **The index.** Both directions as compressed rows (offsets plus neighbours, in `Int32Array`s), built from the import graph describe already loads once per index version (ADR-036), and kept beside it.
**Alternatives:** (a) Files only: an agent asking about an area would have to list its files first. (b) Path order within a distance: a cut list of a hub's thousands of importers would show `build/` and `extensions/` first, whatever matters. (c) No paging and a larger cap: Claude Code moves results of 50,000 characters or more to a file, and a complete list is the point of the tool.
**Consequences:** On VS Code the rows add about 1.4 MB beside the graph, built once per version, and a search over 139,580 imports takes milliseconds (MCP Benchmark #1). Totals are exact for the index, which is as current as the background worker keeps it.
**Revisit when:** agents ask for a subset (the dependents under one folder): add an `under` filter rather than a bigger page.
```

import path from "path";
import type { SummaryStatus } from "../contracts";
import { getDb } from "../db/client";
import { loadFileInfo, sumLinesInside } from "../db/store/map";
import { requireRepository } from "../db/store/structure";
import { readIndexVersion } from "../db/store/version";
import { repoKey } from "../index/paths";
import { describe } from "./describe";
import type { MapReadOptions } from "./level";
import { importIndexFor, type ImportIndex } from "./reach";

/** How many of the most-imported files an overview lists. */
export const MOST_IMPORTED = 10;

/** A top-level folder or file of the repo, with its size. */
export type OverviewArea = { path: string; kind: "folder" | "file"; fileCount: number; lineCount: number; tagline?: string };

/** The first answer about an unfamiliar repo (PIVOT_SPEC.md §6.2's `overview`). */
export type Overview = {
    repo: string;
    name: string;
    tagline?: string;
    summary?: string;
    summaryStatus: SummaryStatus;
    summaryError?: string;
    stats: { fileCount: number; lineCount: number; importCount: number };
    /** The repo's top-level folders and files, in the Map's order (largest first). */
    areas: OverviewArea[];
    /** The files most files import (ADR-010's importance), at most MOST_IMPORTED, none that nothing imports. */
    mostImported: { path: string; importedBy: number }[];
    stalePaths: number;
    indexVersion: number;
};

/** Files by how many files import them, most first, ties by path; files nothing imports are left out. */
export function rankMostImported(index: ImportIndex, limit: number): { path: string; importedBy: number }[] {
    const imported: number[] = [];
    for (let i = 0; i < index.paths.length; i++) if (index.inDegree[i] > 0) imported.push(i);
    return imported
        .sort((a, b) => index.inDegree[b] - index.inDegree[a] || a - b)
        .slice(0, limit)
        .map((i) => ({ path: index.paths[i], importedBy: index.inDegree[i] }));
}

/**
 * The repo's describe answer (its summary, size and top-level children), plus each area's lines and the repo's
 * most-imported files. One read transaction; describe's own runs inside it as a savepoint.
 */
export function overview(repoRoot: string, options: MapReadOptions = {}): Overview {
    const db = getDb();
    const repoId = requireRepository(db, repoKey(path.resolve(repoRoot)));
    return db.transaction(() => {
        const root = describe(repoRoot, "", options);
        const index = importIndexFor(db, repoId, readIndexVersion(db, repoId));
        return {
            repo: root.repo,
            name: path.basename(path.resolve(repoRoot)),
            ...(root.tagline ? { tagline: root.tagline, summary: root.summary ?? "" } : {}),
            summaryStatus: root.summaryStatus,
            ...(root.summaryError ? { summaryError: root.summaryError } : {}),
            stats: { fileCount: root.stats.fileCount, lineCount: root.stats.lineCount, importCount: index.imports.neighbours.length },
            areas: (root.children ?? []).map((child): OverviewArea => ({
                path: child.path,
                kind: child.kind === "folder" ? "folder" : "file",
                fileCount: child.fileCount,
                lineCount: child.kind === "folder" ? sumLinesInside(db, repoId, child.path) : loadFileInfo(db, repoId, child.path)?.lineCount ?? 0,
                ...(child.tagline ? { tagline: child.tagline } : {}),
            })),
            mostImported: rankMostImported(index, MOST_IMPORTED),
            stalePaths: root.stalePaths,
            indexVersion: root.indexVersion,
        };
    });
}

import type { SummaryStatus } from "../contracts";
import { freshnessNote } from "../engine/freshness";

/**
 * Answers stay under this many characters (ADR-047). Claude Code warns past 10,000 tokens and moves a text result of
 * 50,000 characters or more into a file the model has to read back.
 */
export const MAX_ANSWER_CHARS = 40_000;

/** Free mode's line where a summary would go (ADR-043): it says what an API key adds. */
export const SUMMARIES_OFF_LINE = "Summary: none — summaries are off (no ANTHROPIC_API_KEY); a key adds a short summary of every file and folder.";

/** A path as answers write it: folders end in "/", so a reader tells them from files. */
export function shownPath(repoPath: string, kind: "folder" | "file"): string {
    return kind === "folder" ? `${repoPath}/` : repoPath;
}

/** A count as answers write it: 4231 → "4,231". */
export const formatCount = (n: number): string => n.toLocaleString("en-US");

/** The line where a summary goes: its text, or what's in its place. */
export function summaryLine(target: { tagline?: string; summary?: string; summaryStatus: SummaryStatus; summaryError?: string }): string {
    if (target.tagline){
        const text = target.summary ? `${target.tagline} — ${target.summary}` : target.tagline;
        return target.summaryStatus === "stale" ? `${text} (Out of date: changed since it was summarized.)` : text;
    }
    if (target.summaryStatus === "off") return SUMMARIES_OFF_LINE;
    if (target.summaryStatus === "failed") return `Summary: failed${target.summaryError ? ` (${target.summaryError})` : ""}.`;
    return "Summary: not written yet.";
}

/** How many of `lines` to show: at most `limit`, and only as many as fit in `budget` characters, one per line. */
export function fitting(lines: readonly string[], limit: number, budget: number): number {
    let used = 0;
    let count = 0;
    while (count < lines.length && count < limit && used + lines[count].length + 1 <= budget){
        used += lines[count].length + 1;
        count++;
    }
    return count;
}

/** "… 4,231 more", and where the next page starts when the list pages. */
export function moreLine(hidden: number, nextOffset?: number): string {
    return `… ${formatCount(hidden)} more${nextOffset === undefined ? "" : ` (next page: offset ${nextOffset})`}`;
}

/** What a tool's answer is made of, before the call's own notes are added. */
export type AnswerParts = { body: string[]; notes?: string[]; stale?: number };

/**
 * An answer's text (PIVOT_SPEC.md §6.2, ADR-047): the repo note first, because everything after it is about that repo;
 * then the body; then the tool's notes, the index note, and the stale-summary note last.
 */
export function answerText(parts: AnswerParts & { repoNote?: string; indexNote?: string }): string {
    const stale = parts.stale ? freshnessNote(parts.stale) : null;
    const note = (text: string): string => `Note: ${text}`;
    return [
        ...(parts.repoNote ? [note(parts.repoNote)] : []),
        ...parts.body,
        ...(parts.notes ?? []).map(note),
        ...(parts.indexNote ? [note(parts.indexNote)] : []),
        ...(stale ? [note(stale)] : []),
    ].join("\n");
}

/** What became of a show_on_map event (decided by the adapter, ADR-046). */
export type MapDelivery = "shown" | "no-map" | "live-off" | "other-repo";

/** The sentence a show_on_map answer ends with. `mapRepo` and `repo` are names, not roots. */
export function deliveryNote(delivery: MapDelivery, where: { port: number; mapRepo: string | null; repo: string }): string {
    switch (delivery){
        case "shown": return `Sent to the Map at http://localhost:${where.port}; any open Map tab shows it.`;
        case "no-map": return `No Map answered at http://localhost:${where.port}, so nothing is shown. The user can start it with npm run dev in the Nebulosity folder.`;
        case "live-off": return "Nothing was sent: live updates are off in this session (NEBULOSITY_LIVE=off).";
        case "other-repo": return `Nothing was sent: the Map shows ${where.mapRepo ?? "no repository"}, not ${where.repo}. The user can pick ${where.repo} in the Map's repo menu.`;
    }
}

import { plural } from "../index/summarize/prompts";
import { fitting, formatCount, MAX_ANSWER_CHARS, moreLine, shownPath, summaryLine, type AnswerParts } from "./text";

/** How much of each list an answer shows; the counts above a list are always whole (ADR-047). */
export const SHOWN = { areas: 30, children: 20, declarations: 30, linkedAreas: 10 } as const;
/** A search hit's best code, cut to this many characters. */
export const SNIPPET_CHARS = 160;
/** Room kept inside MAX_ANSWER_CHARS for a reach answer's distance headings, page line, cut line and notes. */
const REACH_HEADROOM = 2_000;

/** dependents and dependencies list a page: everything reached, or only the direct files. */

export function overviewAnswer(o: Overview): AnswerParts {
    const body = [
        `${o.name}: ${plural(o.stats.fileCount, "file")}, ${plural(o.stats.lineCount, "line")}, ${plural(o.stats.importCount, "import")} between files.`,
        summaryLine(o),
    ];
    if (o.areas.length > 0){
        body.push("Areas, largest first:");
        for (const area of o.areas.slice(0, SHOWN.areas)){
            const size = area.kind === "folder" ? `${plural(area.fileCount, "file")}, ${plural(area.lineCount, "line")}` : plural(area.lineCount, "line");
            body.push(`  ${shownPath(area.path, area.kind)}  ${size}${area.tagline ? ` — ${area.tagline}` : ""}`);
        }
        if (o.areas.length > SHOWN.areas) body.push(`  ${moreLine(o.areas.length - SHOWN.areas)}`);
    }
    if (o.mostImported.length > 0){
        body.push("Most imported files:");
        for (const f of o.mostImported) body.push(`  ${f.path}  imported by ${formatCount(f.importedBy)}`);
    }
    return { body, stale: o.stalePaths };
}

export function describeAnswer(d: DescribeResponse, repoName: string): AnswerParts {
    const size = `${plural(d.stats.fileCount, "file")}, ${plural(d.stats.lineCount, "line")}`;
    const body = [
        d.kind === "repo" ? `${repoName} — the whole repo: ${size}.`
            : d.kind === "folder" ? `${d.path}/ — folder: ${size}.`
            : `${d.path} — file: ${plural(d.stats.lineCount, "line")}.`,
        summaryLine(d),
    ];

    if (d.children){
        body.push(`Inside (${formatCount(d.children.length)}):`);
        for (const child of d.children.slice(0, SHOWN.children)){
            const label = child.kind === "folder" ? `${child.name}/  ${plural(child.fileCount, "file")}` : child.name;
            body.push(`  ${label}${child.tagline ? ` — ${child.tagline}` : ""}`);
        }
        if (d.children.length > SHOWN.children) body.push(`  ${moreLine(d.children.length - SHOWN.children)}`);
    }

    if (d.symbols){
        if (d.symbols.length === 0) body.push("Declarations: none.");
        else{
            body.push(`Declarations (${formatCount(d.symbols.length)}):`);
            for (const s of d.symbols.slice(0, SHOWN.declarations)){
                const lines = s.startLine === s.endLine ? `${s.startLine}` : `${s.startLine}–${s.endLine}`;
                body.push(`  ${lines}  ${s.kind} ${s.name}${s.exported ? "" : " (not exported)"}`);
            }
            if (d.symbols.length > SHOWN.declarations) body.push(`  ${moreLine(d.symbols.length - SHOWN.declarations)}`);
        }
    }

    // the whole repo has no outside
    if (d.kind !== "repo") body.push(...linkedAreas("Uses", d.uses), ...linkedAreas("Used by", d.usedBy));
    return { body, stale: d.stalePaths };
}

function linkedAreas(label: string, areas: readonly AreaCount[]): string[] {
    if (areas.length === 0) return [`${label}: nothing outside it.`];
    const imports = areas.reduce((sum, area) => sum + area.count, 0);
    const lines = [`${label} (${plural(imports, "import")}):`];
    for (const area of areas.slice(0, SHOWN.linkedAreas)) lines.push(`  ${shownPath(area.path, area.kind)}  ${formatCount(area.count)}`);
    if (areas.length > SHOWN.linkedAreas) lines.push(`  ${moreLine(areas.length - SHOWN.linkedAreas)} areas`);
    return lines;
}

export function searchAnswer(r: SearchResult): AnswerParts {
    const notes = r.note ? [r.note] : [];
    if (r.hits.length === 0) return { body: [`No files or folders match "${r.query}". Try other words; for an exact string, use Grep.`], notes };

    const body = [`Search "${r.query}": ${plural(r.hits.length, "best match", "best matches")}.`];
    r.hits.forEach((hit, i) => {
        body.push(`${String(i + 1).padStart(2)}. ${shownPath(hit.path, hit.kind)}${hit.tagline ? ` — ${hit.tagline}` : ""}`);
        if (hit.code){
            const lines = hit.code.startLine === hit.code.endLine ? `line ${hit.code.startLine}` : `lines ${hit.code.startLine}–${hit.code.endLine}`;
            body.push(`    ${hit.code.symbol}, ${lines}: ${clip(hit.code.snippet, SNIPPET_CHARS)}`);
        }
    });
    return { body, notes };
}

const clip = (text: string, max: number): string => (text.length <= max ? text : `${text.slice(0, max - 1).trimEnd()}…`);

export function reachAnswer(a: ReachAnswer, page: ReachPage): AnswerParts {
    const target = shownPath(a.path, a.kind);
    const total = a.reached.length;
    if (total === 0){
        return { body: [a.direction === "dependents"
            ? (a.kind === "folder" ? `Nothing outside ${target} imports it.` : `Nothing imports ${target}.`)
            : (a.kind === "folder" ? `${target} imports nothing outside it.` : `${target} imports no other indexed file.`)] };
    }

    const body = [a.direction === "dependents"
        ? `${target} is imported${a.kind === "folder" ? " from outside it" : ""} by ${plural(a.direct, "file")} directly and ${plural(total, "file")} in all, counting files that reach it through others.`
        : `${target} imports ${plural(a.direct, "file")}${a.kind === "folder" ? " outside it" : ""} directly and ${plural(total, "file")} in all, counting what those import in turn.`];

    // reached is nearest first, so the direct files lead it
    const listed = page.transitive ? a.reached : a.reached.slice(0, a.direct);
    if (page.offset >= listed.length){
        body.push(`Nothing at offset ${page.offset}: the list has ${formatCount(listed.length)}.`);
        return { body };
    }

    const rest = listed.slice(page.offset);
    const lines = rest.map((r) => `  ${r.path}`);
    const shown = fitting(lines, page.limit, MAX_ANSWER_CHARS - REACH_HEADROOM - body[0].length);
    if (page.offset > 0) body.push(`Showing ${formatCount(page.offset + 1)}–${formatCount(page.offset + shown)} of ${formatCount(listed.length)}.`);

    const atDistance = new Map<number, number>();
    for (const r of a.reached) atDistance.set(r.distance, (atDistance.get(r.distance) ?? 0) + 1);
    let group = 0;
    for (let i = 0; i < shown; i++){
        if (page.transitive && rest[i].distance !== group){
            group = rest[i].distance;
            body.push(`Distance ${group} (${formatCount(atDistance.get(group) ?? 0)}):`);
        }
        body.push(lines[i]);
    }

    const hidden = listed.length - page.offset - shown;
    if (hidden > 0) body.push(moreLine(hidden, page.offset + shown));
    return { body };
}

export function chainAnswer(c: ChainAnswer): AnswerParts {
    const from = shownPath(c.from, c.fromKind);
    const to = shownPath(c.to, c.toKind);
    if (c.found === "none") return { body: [`No chain of imports joins ${from} and ${to}, in either direction.`] };

    const steps = plural(c.files.length - 1, "step");
    const body = [c.found === "forward"
        ? `${from} reaches ${to} in ${steps}:`
        : `${from} doesn't reach ${to} through imports; the other way round, ${to} reaches ${from} in ${steps}:`];
    body.push(`  ${c.files[0]}`);
    for (let i = 1; i < c.files.length; i++) body.push(`  → ${c.files[i]}  (import "${c.specifiers[i - 1]}")`);
    return { body };
}

/** One spelling for comparing folders: forward slashes, no trailing slash, and on Windows any case (C:\ is c:/). */
export function sameFolderKey(p: string, platform: NodeJS.Platform = process.platform): string {
    const slashed = normalizeSlashes(p).replace(/\/+$/, "");
    return platform === "win32" ? slashed.toLowerCase() : slashed;
}

/** How a call's repo was picked (ADR-046). */
export type RepoChoice = { root: string; how: "project" | "map" };

/**
 * Which indexed repo a call answers about (ADR-046): the one holding the project folder (the deepest, when indexed repos
 * nest), else the Map's active repo, else none. Pure: the caller passes what it read.
 */
export function chooseRepo(projectDir: string, indexedRoots: readonly string[], activeRoot: string | null, platform: NodeJS.Platform = process.platform): RepoChoice | null {
    const key = (p: string): string => sameFolderKey(p, platform);
    const here = key(projectDir);
    const holding = indexedRoots
        .filter((root) => here === key(root) || here.startsWith(`${key(root)}/`))
        .sort((a, b) => key(b).length - key(a).length)[0];
    if (holding !== undefined) return { root: holding, how: "project" };

    const active = activeRoot === null ? undefined : indexedRoots.find((root) => key(root) === key(activeRoot));
    return active === undefined ? null : { root: active, how: "map" };
}

/** Everything one tool call needs, read fresh: a new index or a repo switch takes effect without a restart. */
export type CallSetup = {
    context: ToolContext;
    /** Whether live events may go out (only for the repo the Map shows), where to, and the Map's repo's name. */
    live: { allowed: boolean; port: number; mapRepo: string | null };
};

export function setupCall(projectDir: string): CallSetup {
    const config = readConfig();
    const roots = listStagedRepositories(getDb()).map((r) => r.rootPath);
    const choice = chooseRepo(projectDir, roots, config.activeRepo);
    if (choice === null) throw new NoActiveRepoError();

    const status = readIndexStatus(choice.root);
    const structure = status?.stages.structure;
    const name = path.basename(choice.root);
    const indexNote = structure?.state === "running"
        ? `The index is being updated (${structure.done}/${structure.total} files), so answers may miss the newest changes.`
        : structure?.state === "failed"
            ? `The last index update failed${structure.note ? ` (${structure.note})` : ""}, so answers may be out of date. Running npm run index in the Nebulosity folder redoes it.`
            : undefined;

    return {
        context: {
            repoRoot: choice.root,
            summariesOff: status?.stages.summaries.state === "off",
            ...(choice.how === "map" ? { repoNote: `Answering about ${name} (${choice.root}), the repo the Map shows: the project folder ${normalizeSlashes(projectDir)} isn't inside an indexed repo.` } : {}),
            ...(indexNote ? { indexNote } : {}),
        },
        live: {
            allowed: config.activeRepo !== null && sameFolderKey(config.activeRepo) === sameFolderKey(choice.root),
            port: config.port,
            mapRepo: config.activeRepo === null ? null : path.basename(config.activeRepo),
        },
    };
}

## ADR-046 — An MCP call answers about the repo Claude Code is in, else the Map's repo (‹today›)

**Context:** Claude Code starts the MCP server once per session, in whatever project the user opened, and sets `CLAUDE_PROJECT_DIR` to that project's root for the servers it starts. The index can hold several repos; the Map shows one, the config's `activeRepo` (PIVOT_SPEC.md §7.1). Live events carry paths but no repo (API_CONTRACTS.md §14), so an event about one repo lights boxes with the same paths in another.
**Decision:**
- Each call reads the indexed repos and the config afresh. It answers about the repo holding the project folder (`CLAUDE_PROJECT_DIR`, else the working folder), the deepest when indexed repos nest. Folders compare by forward-slash spelling without a trailing slash, and case-insensitively on Windows.
- Otherwise it answers about the Map's repo, and the answer's first line says so, naming both folders. Otherwise it's an error: nothing indexed yet.
- Live events go to the config's port, read per call, and only when the answering repo is the Map's. `show_on_map` says when the Map shows another repo.
- Free mode is the stored summaries stage: `off` means no key (ADR-043), so the server never loads `.env.local` or holds the key.
- An index update in progress or failed is noted after every answer.
**Alternatives:** (a) Always the Map's repo: Claude Code opened in another indexed repo would get answers about the wrong one, with nothing said. (b) A `repo` argument on every tool: more for the model to get wrong. (c) A repo fixed per registration (`-e`): one registration per repo. (d) A `repo` field on live events, with the Map ignoring others': a contract change for a case this rule already prevents.
**Consequences:** One user-scope registration serves every indexed repo, and `npm run index` or the Map's repo menu take effect without restarting Claude Code. Each call pays a few small reads (well under a millisecond).
**Revisit when:** someone runs two Maps on different ports, or wants the Map to follow Claude Code's repo by itself.

## ADR-047 — One registry entry per tool, answering in compact text (‹today›) — amends ADR-030

**Context:** ADR-030 puts each tool in `lib/tools/registry.ts` once, wrapped by MCP now and by LangGraph in E1. Two things weren't settled. What a handler returns, given that the MCP server must also tell the Map (§8) and the Guide will turn UI actions into `ui_action` events (API_CONTRACTS.md §5). And what the answer text looks like: PIVOT_SPEC.md §6.2 asks for compact plain text, exact totals, truncation markers and a freshness note last.
**Decision:**
- An entry is `{ name, description, inputSchema (zod), handler(input, context) }`. The context names the repo, says whether summaries are off, and carries any repo or index note (ADR-046). The handler returns `{ text, paths, action? }`: the answer, the paths it touched, and show_on_map's UI action. It never touches the network: the MCP adapter posts the live event, and E1's adapter will emit `ui_action`.
- The text rules are API_CONTRACTS.md §17: plain text; repo-relative paths, folders ending in "/"; exact counts with separators; lists cut with "… N more" and the next offset where the tool pages; under 40,000 characters; notes last, with the stale-summary note very last, except the repo note, which comes first.
- Free mode answers everything (ADR-043). Where a summary would go, the answer says summaries are off and what a key adds; search says it used code and folder names.
- One pure builder per tool (`lib/tools/answers.ts`) turns engine results into text, so the format is tested without a database.
- `lib/agent/tools.ts` (the owner's Phase 5 tools) stays as it is until E1 replaces it with wrappers over this registry.
**Alternatives:** (a) JSON answers (`structuredContent`): exact, but larger, and a model skims prose faster. (b) Handlers that post live events themselves: the Guide's in-process adapter would then make HTTP calls to its own server. (c) Markdown: tokens spent on syntax.
**Consequences:** A new tool is one entry and one builder. The text is a contract (§17), tested on the fixture.
**Revisit when:** a client wants structured results (an IDE view of a dependents list, say): add an `outputSchema` beside the text.
```

| `dependents` | `path`, `transitive` (false), `limit` 1–500 (50), `offset` (0) | the direct and total counts, then the files: nearest first, most imported next, by path last; grouped by distance when transitive |
| `dependencies` | the same | the same, following what the target imports |
| `path` | `from`, `to` | the shortest chain of imports with each step's specifier, the other direction when needed, or "no chain" |
| `show_on_map` | `action`: highlight, focus or clear (highlight); `paths` (0–50) | what was sent, what was left out, and whether the Map took it |

**Paths.** Inputs are repo-relative. Backslashes, a leading `./` and a trailing `/` are accepted (`parseRepoPath`); `..`, absolute and drive-letter paths are refused. `""` is the repo root; `dependents`, `dependencies` and `path` refuse it, since the whole repo has no outside.

**Answers.**
- Plain text with no Markdown. Repo-relative paths, folders ending in `/`.
- Exact counts with thousands separators. A count always covers everything, even when the list under it is cut.
- A cut list ends with `… N more`, plus `(next page: offset K)` where the tool pages.
- Every answer stays under 40,000 characters.
- Notes are lines starting `Note: `. When the project folder didn't pick the repo, that note comes first. Then the answer, then the tool's own notes, then the index note (an update in progress or failed), and the stale-summary note last.
- With no API key, the line where a summary would go reads `Summary: none — summaries are off (no ANTHROPIC_API_KEY); a key adds a short summary of every file and folder.`

**Errors.** An MCP error result (`isError: true`) with one sentence. The cases:
- nothing indexed yet (with Nebulosity's folder);
- an index older than the checkout;
- nothing indexed at a path;
- a path outside the repo;
- overlapping places for `path`;
- bad `show_on_map` input;
- the MCP SDK's "Input validation error" for input outside a schema.

**Live events** (§14). One per successful call: `tool` is the bare name and `paths` what the call touched. describe sends its path; search its hits; dependents and dependencies the target; path `from`, `to`, then the chain between; show_on_map its paths and its `action`; overview none. None go out when the answer's repo isn't the one the Map shows, or with `NEBULOSITY_LIVE=off`. Pulses are fire-and-forget; show_on_map waits (at most 200 ms) to say whether the Map took it.

/**
 * The MCP adapter (PIVOT_SPEC.md §6.2, ADR-030): the tool registry, served to Claude Code and any MCP client over stdio.
 * Thin by rule (§3, rule 2): each call picks its repo, runs one registry entry, posts one live event, and returns text.
 */
import path from "path";
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import type { LiveEvent } from "../lib/contracts";
import { useReadOnlyDatabase } from "../lib/db/client";
import { errorResponseFor } from "../lib/engine/errors";
import { nebulosityHome } from "../lib/home";
import { postLiveEvent } from "../lib/live/client";
import { SERVER_INSTRUCTIONS, TOOLS } from "../lib/tools/registry";
import { setupCall } from "../lib/tools/repo";
import { deliveryNote, type MapDelivery } from "../lib/tools/text";

/** package.json's version (a test keeps them equal). */
export const SERVER_VERSION = "0.1.0";

/** Sends one live event to the Map's server on `port`; true when it took it (lib/live/client.ts). */
export type LivePoster = (event: LiveEvent, port: number) => Promise<boolean>;

export type ServerOptions = {
    /** The folder Claude Code runs in: it picks the repo (ADR-046). */
    projectDir: string;
    /** false: never post a live event (NEBULOSITY_LIVE=off), for benchmarks and smoke tests while a Map is open. */
    live: boolean;
    post?: LivePoster;
    now?: () => Date;
};

export function createServer(options: ServerOptions): McpServer {
    const server = new McpServer({ name: "nebulosity", version: SERVER_VERSION }, { instructions: SERVER_INSTRUCTIONS });
    const post: LivePoster = options.post ?? ((event, port) => postLiveEvent(event, { port }));
    const now = options.now ?? (() => new Date());

    for (const tool of TOOLS){
        server.registerTool(
            tool.name,
            { description: tool.description, inputSchema: tool.inputSchema, annotations: { readOnlyHint: true, openWorldHint: false } },
            async (input) => {
                try{
                    const call = setupCall(options.projectDir);
                    const output = await tool.handler(input, call.context);
                    const event: LiveEvent = { tool: tool.name, paths: output.paths, at: now().toISOString(), ...(output.action ? { action: output.action } : {}) };

                    if (!output.action){
                        // a pulse on the open Map: fire and forget, so no answer waits on it
                        if (options.live && call.live.allowed) void post(event, call.live.port);
                        return { content: [{ type: "text" as const, text: output.text }] };
                    }

                    // show_on_map says what became of its event, so it waits (at most the poster's 200 ms)
                    const delivery: MapDelivery = !options.live ? "live-off"
                        : !call.live.allowed ? "other-repo"
                        : (await post(event, call.live.port)) ? "shown" : "no-map";
                    const note = deliveryNote(delivery, { port: call.live.port, mapRepo: call.live.mapRepo, repo: path.basename(call.context.repoRoot) });
                    return { content: [{ type: "text" as const, text: `${output.text}\n${note}` }] };
                } catch (err){
                    return { content: [{ type: "text" as const, text: errorText(err) }], isError: true };
                }
            },
        );
    }

    return server;
}

/** An error as one sentence for the model. Unexpected ones are logged to stderr with their stack. */
export function errorText(err: unknown): string {
    const { status, error } = errorResponseFor(err);
    if (status === 500) console.error(err);
    return error.code === "INDEX_EMPTY" ? `${error.message} (Nebulosity's folder: ${nebulosityHome()}.)` : error.message;
}

/** stdout carries the protocol, so anything else written there breaks it: console output goes to stderr (ADR-048). */
export function keepStdoutForProtocol(): void {
    const toStderr = (...args: unknown[]): void => console.error(...args);
    console.log = toStderr;
    console.info = toStderr;
    console.debug = toStderr;
}

/** The stdio entry point that mcp/launch.mjs runs. */
export async function main(): Promise<void> {
    keepStdoutForProtocol();
    useReadOnlyDatabase();
    const server = createServer({ projectDir: process.env.CLAUDE_PROJECT_DIR || process.cwd(), live: process.env.NEBULOSITY_LIVE !== "off" });
    // a client stops us by closing stdin (Claude Code on Windows then kills the process tree after 300 ms): leave at once
    process.stdin.on("end", () => {
        void server.close().finally(() => process.exit(0));
    });
    await server.connect(new StdioServerTransport());
}
```

```markdown
## ADR-048 — The MCP server starts as `node <checkout>/mcp/launch.mjs` (‹today›)

**Context:** Claude Code runs an MCP config's command from the user's project folder. The engine is TypeScript run by tsx, a devDependency that only the checkout has. On Windows, `npx` is a `.cmd` batch file, so a config that starts `npx` needs `cmd /c`.
**Decision:**
- A plain-JavaScript launcher, `mcp/launch.mjs`, run by `node`. It sets `NEBULOSITY_HOME` to the checkout it sits in unless that's already set, imports tsx from the checkout (an ESM import resolves next to the importing file, not from the working folder), then runs `mcp/server.ts`'s `main()`.
- The server speaks MCP over stdio through `@modelcontextprotocol/sdk` 1.32.1, pinned exactly. Before anything else, it sends `console.log`, `info` and `debug` to stderr: stdout carries protocol messages only.
- It exits when the client closes stdin. On Windows, Claude Code (2.1.296) kills the process tree 300 ms after closing it.
- One line registers it on every OS: `claude mcp add --scope user --transport stdio nebulosity -- node <checkout>/mcp/launch.mjs`.
**Alternatives:** (a) `cmd /c npx tsx …/mcp/server.ts`: a Windows-only line, npx's lookup on every start, and tsx found only if the working folder has it. (b) Compile to `dist/` and run plain JavaScript: no tsx at run time, but a build step before every use. V1.6's package decides that.
**Consequences:** Start-up costs tsx's load plus the engine's first transpile (about 0.5 s; tsx caches it after). The server needs the checkout's `node_modules`, a local tool's normal state.
**Revisit when:** V1.6 ships an installable package (a `bin` entry replaces the launcher), or Node runs the engine's TypeScript without tsx.
```

 * npm run bench-mcp -- [path-to-repo]   (default ../vscode)
 *
 * S5 (PIVOT_SPEC.md §2): every tool's latency through the real MCP server, as a client sees it. The SDK's stdio client

import path from "path";
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";
import { nebulosityPath } from "../lib/home";

const WARM_CALLS = 20;
const S5_MS = 500;

const FILES = [
    "src/vs/base/common/lifecycle.ts", "src/vs/base/common/event.ts", "src/vs/base/common/uri.ts",
    "src/vs/platform/instantiation/common/instantiation.ts", "src/vs/editor/common/core/range.ts",

    "src/vs/workbench/browser/parts/editor", "src/vs/platform/files", "extensions/git", "build", "src/vs/code",

    "integrated terminal", "editor tabs", "extension host", "file watcher", "keybinding resolution",
    "lifecycle", "settings editor", "git blame", "debug adapter", "notebook kernel",
];
const PAIRS: [string, string][] = [
    ["src/vs/workbench/contrib/terminal", "src/vs/base/common/lifecycle.ts"],
    ["src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts", "src/vs/platform/instantiation/common/instantiation.ts"],

    ["overview", [{}]],
    ["describe", [...FOLDERS, ...FILES].map((p) => ({ path: p }))],
    ["search", QUERIES.map((query) => ({ query }))],
    ["dependents", FILES.flatMap((p) => [{ path: p }, { path: p, transitive: true }])],
    ["dependencies", FILES.flatMap((p) => [{ path: p }, { path: p, transitive: true }])],
    ["path", PAIRS.map(([from, to]) => ({ from, to }))],
    ["show_on_map", [...FILES, ...FOLDERS].map((p) => ({ paths: [p] }))],
];

/** Nearest-rank percentile of sorted values. */
const percentile = (sorted: number[], q: number): number => sorted[Math.max(0, Math.ceil(q * sorted.length) - 1)];
const ms = (n: number): string => `${n.toFixed(0)} ms`;

async function timed(client: Client, name: string, args: Record<string, unknown>): Promise<{ ms: number; chars: number }> {
    const started = performance.now();
    const result = await client.callTool({ name, arguments: args });
    const took = performance.now() - started;
    const text = (result.content as { type: string; text: string }[])[0]?.text ?? "";
    if (result.isError) throw new Error(`${name} ${JSON.stringify(args)} failed: ${text}`);
    return { ms: took, chars: text.length };
}

async function main(): Promise<void> {
    const repo = path.resolve(process.argv[2] ?? path.join("..", "vscode"));
    const env: Record<string, string> = {};
    for (const [key, value] of Object.entries(process.env)) if (value !== undefined) env[key] = value;

    const client = new Client({ name: "bench-mcp", version: "1" });
    const started = performance.now();

        command: process.execPath,
        args: [nebulosityPath("mcp", "launch.mjs")],
        cwd: repo,
        env: { ...env, NEBULOSITY_LIVE: "off", CLAUDE_PROJECT_DIR: repo },
        stderr: "inherit",
    }));
    const startupMs = performance.now() - started;

    const rows: string[] = [];
    let worst = 0;
    for (const [name, inputs] of CALLS){
        const first = await timed(client, name, inputs[0]);
        const warm: { ms: number; chars: number }[] = [];
        for (let i = 0; i < WARM_CALLS; i++) warm.push(await timed(client, name, inputs[(i + 1) % inputs.length]));
        const sorted = warm.map((w) => w.ms).sort((a, b) => a - b);
        const largest = Math.max(first.chars, ...warm.map((w) => w.chars));
        worst = Math.max(worst, sorted[sorted.length - 1]);
        rows.push(`| \`${name}\` | ${ms(first.ms)} | ${WARM_CALLS} | ${ms(percentile(sorted, 0.5))} | ${ms(percentile(sorted, 0.95))} | ${ms(sorted[sorted.length - 1])} | ${largest.toLocaleString("en-US")} |`);
    }
    await client.close();

    console.log(`Server start (spawn → initialized): ${ms(startupMs)}\n`);
    console.log("| Tool | First call | Warm calls | p50 | p95 | max | Largest answer (chars) |");
    console.log("|---|---|---|---|---|---|---|");
    for (const row of rows) console.log(row);
    const pass = worst <= S5_MS;
    console.log(`\nS5 (every warm call ≤ ${S5_MS} ms): ${pass ? "PASS" : "FAIL"} (worst ${ms(worst)})`);
    process.exit(pass ? 0 : 1);
}

main().catch((err) => {
    console.error(err);
    process.exit(1);
});
